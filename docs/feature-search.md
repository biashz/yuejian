# 跨书全文检索 — 功能规划

> 对应 [product-spec.md](product-spec.md) 功能地图 P2「扩展」的第一项：全文检索（跨书）。

## 1. 定位

书架到几十本之后，「这本书里好像写过」比「这本书叫什么」更常用。原先的搜索框只匹配书名与作者，正文一个字都搜不到；侧栏的搜索又只作用于当前打开的那一本。

这一期把搜索框升级成**两件事**：书名筛选照旧，正文命中单独成区。

## 2. 两条取数路径

不建统一的倒排索引，是因为四类格式的成本完全不同：

| 类型 | 路径 | 为什么 |
| --- | --- | --- |
| 文本 / Markdown / CSV / 代码 | Rust `search_text` 按需扫 | 正文能解码，按行索引流式扫即可；一份 100MB 日志也不必先存全文副本 |
| PDF | pdf.js 逐页抽文本 → 缓存 → 找子串 | 压缩对象流，Rust 侧没有解析器；pdf.js 已经是现成依赖 |
| 电子书（EPUB / FB2 / MOBI） | foliate `makeBook` 逐节取正文 → 缓存 | 打包的 XHTML，解包逻辑在 foliate 里，再写一份 Rust 版等于维护两套 |
| CBZ | 索引为空 | 固定版面没有字符流，本来就没有可搜的文字 |

前一类**不需要索引**，后两类需要——它们的共同点是「解一次很贵，且解它的工具在前端」。

## 3. 索引

落盘在 `data/search/<bookId>.json`，由 Rust 的 `read_search_index` / `write_search_index` 存取，文件格式：

```jsonc
{
  "v": 1,                 // 结构版本；改了形状就 +1，旧缓存自动作废
  "size": 2483102,        // 抽取时的文件体积
  "mtime": 1762300000000, // 抽取时的修改时间
  "units": [
    { "label": "", "page": 12, "href": "", "text": "第 12 页的正文……" },
    { "label": "第三章", "page": 0, "href": "OEBPS/ch3.xhtml", "text": "……" }
  ]
}
```

**单元**而不是一整段全文：PDF 一页一个单元，电子书一节一个单元。检索因此知道命中落在第几页、哪一章——这是把全文拼成一个大字符串换不来的。

**失效判据是 `size` + `mtime`**，两者都对得上才复用。`Book.mtime` 是这一期新增的字段（`#[serde(default)]`，旧数据读出来是 0）：0 与任何真实 mtime 都不相等，因此旧书架天然被当作「索引可能过期」，重建一次即可，不需要迁移代码。

上限：

| 项 | 值 | 理由 |
| --- | --- | --- |
| 每本索引字符数 | 600 000 | 60 万字已远超「检索得到」的需要，再存只是占盘 |
| PDF 页数 | 1200 | 防一份异常文件把索引过程拖成几分钟 |
| 电子书节数 | 400 | 同上 |
| 每本命中条数 | 5 | 再多就把别处挤没了 |
| 列出几本 | 8 | 一屏之外的命中先不列，避免结果区变成第二条书架 |

## 4. 交互

- **关键词至少两个字**才搜正文。单字在几十本书里能命中上千处，既慢又没有信息量。
- **320ms 防抖**，且每次输入立刻作废旧的一轮（`token.cancelled`）。不做这件事，用户会在几轮搜索后看到上一个关键词的结果。
- **范围跟随筛选**：分类轴与类型轴选中什么，就搜什么范围内的书。否则会出现「筛了 PDF，结果里冒出 EPUB」。
- **进度可见**：索引可能要几秒，主区先显示「正在建立索引 42% · 书名」，而不是一声不响。
- **单本失败不拖垮整轮**：DRM、文件被删、PDF 结构坏，都只跳过那一本，并在抬头里报「N 本未能参与检索」。
- **点命中**：打开这本书 → **落到那一处** → 把关键词填进侧栏搜索。

一次点击做三件事，因为它们的可靠性不同：

| 动作 | 依据 | 覆盖 |
| --- | --- | --- |
| 定位 | PDF 页码 / 文本行号 / 电子书章节 `href` | PDF、窗口化文本、电子书 |
| 高亮 | 侧栏搜索（把这本里所有命中标出来） | 全部 |
| 聚焦 | 侧栏里对应的那一条加 `is-focus` 并滚进视野 | PDF、文本 |

**Markdown 只有「高亮」**：检索拿到的是**源码行号**，而渲染后的 DOM 与源码行没有对应关系（表格、脚注、代码块都会改变行数），按行号滚过去必然错位。宁可交给侧栏搜索定位，也不给一个看起来精确、实际错位的位置。

**普通文本（非窗口化）也只有高亮**：整篇里的行号要换算成滚动位置，只有窗口化渲染那一套才有这个映射。

定位**延后两帧**执行，不是保险起见：`openText` 在打开末尾用 `requestAnimationFrame` 把滚动位置恢复成上次进度，那一帧晚于打开动作完成——过早设的滚动位置会被它冲掉，表现为「点了命中，书开了，却停在第一行」。PDF 恢复页码同理。

## 5. 不做

- **不做倒排索引**。子串扫描在十万量级字符上是微秒级，倒排索引带来的分词、增量更新、语言差异全是成本。真到了需要排序相关性的规模再说。
- **不做增量更新**。文件变了整本重抽——一次几秒，而增量更新的失效判断比重抽更容易错。
- **不做跨书结果的按相关性排序**。顺序按书架原有排序（最近打开），用户认得这个顺序。

## 6. 模块划分

| 文件 | 职责 |
| --- | --- |
| `src/js/library-index.js` | 抽取与缓存：PDF 逐页、电子书逐节；判过期；纯函数 `joinItems` / `isFresh` |
| `src/js/library-search.js` | 取数编排：两条路径统一成 `{book, hits}`；`snippet` 切三段 |
| `src/js/library-hits.js` | 命中区渲染（幂等重画；状态行单独更新） |
| `src/js/library-search-ui.js` | 防抖、作废、进度文案、点命中的跳转 |
| `src-tauri/src/commands.rs` | `read_search_index` / `write_search_index`；`remove_book` 顺手删索引 |

调度单独一个模块，是因为触发点不止一处——关键词、类型筛选、分类筛选都会改变「搜什么 / 搜哪些书」，而它们分属两个 bind 文件。

## 7. 验收

| 项 | 标准 |
| --- | --- |
| 命中区 | 书名 + 行号 / 页码 + 带 `<mark>` 的片段；位于书网格之后，不与书名筛选混排 |
| 路径 | 文本 / Markdown 只调 `search_text`，不读不写索引 |
| 片段 | 前后各留 34 / 56 字符，被截断的一侧带省略号 |
| 拼接 | 英文单词之间补空格，CJK 直接相接，`hasEOL` 才换行 |
| 失效 | `size` 或 `mtime` 任一不同即重建；`mtime === 0` 一律当过期 |
| 跳转 | 点命中打开对应书并落到那一处：文本落到行、PDF 落到页、电子书落到章节；侧栏搜索框已填好关键词，对应条目带 `is-focus` |
| 时序 | 定位在打开动作之后两帧执行，不被 `openText` 的进度恢复冲掉 |
| 空态 | 书名一条没匹配、正文有命中时，书网格的空态改成「书名里没有匹配 / 正文命中见下方」，不说「没有匹配的文档」 |
| 收起 | 清空关键词后命中区整段消失，不留空壳 |
