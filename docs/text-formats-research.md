# 文本格式支持 · 技术调研

> 目标：在不引入重量级解析器的前提下，让阅笺能打开「除 PDF / Markdown 之外的常见文本文件」，
> 并且对中文用户最容易踩的两个坑（GBK 编码、超大日志）给出明确方案。
>
> 现状基线：v0.1.25，`src-tauri/src/commands.rs` + `src/js/reader/open.js`。

## 1. 现状盘点

| 环节 | 现在怎么做的 | 对文本格式的约束 |
| --- | --- | --- |
| 类型判定 | `detect_kind()` 只认 `pdf` / `md` / `markdown` / `mdown`（commands.rs:38） | 其它扩展名直接报「不支持的文件类型」 |
| 选择文件 | `pick_files()` 的 `add_filter` 写死 4 个扩展名（commands.rs:108） | 对话框里根本选不到 `.txt` |
| 读取 | 一律 `fs::read_to_string`，上限 `MAX_TEXT_SIZE = 16MB`（commands.rs:10/197） | **GBK / UTF-16 文件直接失败**（不是有效的 UTF-8）；大文件直接拒绝 |
| 渲染 | comrak 整篇转 HTML，字符串一次性塞进 DOM（markdown.rs / reader-md.js） | 只能处理有标记语法的文档，纯文本没有「行」的概念 |
| 高亮 | `src/vendor/highlight/highlight.min.js`（hljs 11.11.1，common build，约 126KB） | 已有现成能力，代码类文件白拿 |
| 进度 | 按 `ratio`（滚动比例）存 `Book.progress`（store.rs） | 文本类可直接复用，无需改数据结构 |
| 搜索 | Markdown 走 DOM 遍历（ctx.js `runFind`） | 虚拟滚动的长文本没有完整 DOM，搜索必须下沉到 Rust |

结论：**判定 → 读取 → 渲染**三处都要动，其中「读取」是真正的技术核心，其余是适配。

## 2. 格式范围：先划一条线

用户说的「常见文本格式」，实际是三类完全不同的东西，实现成本差一个量级：

| 类别 | 扩展名 | 本质 | 成本 |
| --- | --- | --- | --- |
| **纯文本族** | `txt` `text` `log` `nfo` `readme` `csv` `tsv` | 一段字节 + 需要猜编码 | 低（本轮） |
| **代码 / 配置** | `json` `yml` `yaml` `toml` `ini` `conf` `env` `py` `js` `ts` `tsx` `jsx` `rs` `go` `java` `c` `h` `cpp` `cs` `php` `rb` `sh` `bash` `ps1` `sql` `css` `scss` `less` `html` `xml` `vue` `lua` | 同上 + 语言识别 | 低（hljs 已在本地） |
| **富文本 / 容器** | `rtf` `docx` `epub` `odt` | zip / 二进制 + 自有标记语言，需要解析器 | 高（另立一期） |

本轮只做前两类。理由是后两类要么需要新增 zip + XML 解析依赖（docx/epub），要么需要写 RTF 控制字解析器，
与「文本格式」这个诉求不是一回事；把它们塞进来会把这一轮的风险从「读写文件」拉高到「实现一个渲染引擎」。

## 3. 核心难点一：编码

这是中文用户最真实的痛点：Windows 记事本默认 ANSI（简中 = GBK/CP936）存出来的 `.txt`，用 UTF-8 读会得到
乱码或直接报错。当前代码是 `fs::read_to_string`，遇到 GBK 会返回 `stream did not contain valid UTF-8`，
用户看到的是一行不知所云的错误。

**方案：BOM → 探测器 → 解码器 三级流水线**

1. 先看 BOM：`EF BB BF` = UTF-8、`FF FE` = UTF-16LE、`FE FF` = UTF-16BE。BOM 是硬证据，优先采信。
2. 没有 BOM 时用 `chardetng`（Firefox 的编码探测算法，纯 Rust，没有运行时开销）对**前 8KB** 做猜测，
   得到候选编码 + 一个 `Encoding`。
3. 用 `encoding_rs`（同样来自 Firefox，GB18030 / Big5 / Shift_JIS / EUC-KR 全支持）实际解码，
   解码失败或出现大量 U+FFFD 时回退 `decode_lossy`，保证「一定能显示」，而不是弹错误。

新增依赖：`encoding_rs 0.8` + `chardetng 0.1`。两者都是 Firefox 在用的成熟实现，无 unsafe 传递链问题，
体积上 `encoding_rs` 约给二进制增加 300–400KB（它带完整码表）。

**必须配套的 UI**：工具栏/信息面板里显示「识别为 GB18030」，并允许手动改成 UTF-8 / GB18030 / Big5。
探测不是 100% 准确的（短文件尤甚），用户要有一条自救的路。

**顺带修复**：`.md` 也会遇到 GBK，同一条流水线直接受益——这属于既有缺陷，不是新功能。

## 4. 核心难点二：大文件

`.log` 动辄 50–500MB。整篇读进内存 → 转 HTML → 塞 DOM，三个环节都会炸（当前 16MB 上限就是为了挡这个）。

**分层策略**

| 体积 | 策略 | 依据 |
| --- | --- | --- |
| ≤ 2MB | 全量解码 + 全量渲染（含语法高亮） | 一次性成本可忽略，体验最好 |
| 2–32MB | 全量解码（内存里一份字符串），**前端虚拟滚动**按行渲染，高亮只作用于可视窗口 | 32MB 字符串 ≈ 64MB 内存，可接受 |
| > 32MB | **Rust 侧窗口读取**：`read_text_window(path, byteStart, byteEnd)` 返回指定字节区间；前端只持有可视窗口 ± 500 行 | 内存恒定，与文件大小无关 |

窗口读取可以直接复用 `read_pdf_range` 的模式（`tauri::ipc::Response` 返回裸字节，已有先例，见 commands.rs:398）。
按字节而不是按行定位，是因为正确定位到「第 N 行」需要在 Rust 侧维护行偏移表；折中做法是
**先建采样索引**（每 1024 行记一次字节偏移，100 万行也只占 8KB），再 seek 到最近的采样点后顺序扫。

**虚拟滚动的前提**：行高必须固定（等宽字体 `line-height: 1.6`），这样才能用「绝对定位 + 上下占位块」实现，
不需要测量每一行。正文模式（软换行）的行高不固定，所以**软换行在 > 2MB 时自动关闭**，工具栏给出提示。

## 5. 核心难点三：渲染与高亮

- **纯文本**：不能 `innerHTML`（每行都要转义，且会触发 HTML 解析）。用 `textContent` 逐行填充 `<div>`，
  或者整段放进 `<pre>` 让浏览器自己排版。逐行 `<div>` 是虚拟滚动的前提，选它。
- **语法高亮**：hljs 的高亮是**有状态的**（多行字符串、块注释跨行）。只高亮可视窗口会导致窗口边界的
  高亮错乱。因此：≤2MB 全量高亮；超过则关闭高亮并改成纯文本着色（行号 + 日志级别着色），
  工具栏明确写「大文件已关闭语法高亮」——比悄悄错乱好。
- **语言识别**：扩展名 → hljs 语言别名一张表即可，`yml → yaml`、`sh → bash`、`ts → typescript`。
  认不出来就走 plaintext，不猜内容（猜错的高亮比不高亮更干扰阅读）。
- **CSV/TSV**：自己写一个 RFC 4180 的最小解析器（引号包裹、`""` 转义、CRLF），约 60 行，
  不值得为此引入 `csv` crate。分隔符靠扩展名 + 首行计数猜一次，表格用粘性表头。
- **二进制伪装**：前 8KB 里出现 NUL 字节就判定「这不是文本」，直接给一句可读的提示，不要试图渲染。

## 6. 搜索

现有实现是把 DOM 遍历一遍找文本节点。虚拟滚动下没有完整 DOM，所以文本类的搜索必须下沉：

- ≤2MB：仍走前端 DOM（复用现有逻辑，零改动）。
- 大文件：Rust 侧 `search_text(path, query, limit)`，分块扫描 + 返回「行号 + 片段」，
  点击结果跳到该行（配合采样索引 seek）。

这一条可以放到二期，一期先保证「已加载窗口内可搜索」。

## 7. 进度与书架

- `Book.progress.ratio` 对文本类天然适用；分页号 `page` 复用为「行号」会让语义混乱，
  建议文本类只用 `ratio`，`pages` 存 0。
- `Book.kind` 需要新增取值。前端 `KIND_LABEL` / `KIND_CLASS` / 筛选 chip / 封面角标 / 图标
  都按 kind 分支，要同步补（constants.js:7、shelf.js:78、palette.js:37）。
- 筛选 chip 现在是 `全部 / PDF / MARKDOWN / 收藏`，加一个「文本」即可，不必按扩展名细分。

## 8. 风险清单

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 编码探测误判 | 短文件、纯 ASCII 混少量中文 | 信息面板显示探测结果 + 手动切换编码 |
| BOM 文件首个字符异常 | 显示 `\u{FEFF}` | 解码时剥 BOM |
| 行尾混合 CRLF/LF | 行号错位 | 统一在解码后按 `\n` 切，剥 `\r` |
| 超大 JSON 格式化 | 内存翻倍 | 超过 2MB 不做 pretty-print，原样显示 |
| 高亮状态跨窗口 | 颜色错乱 | 见 §5，超限直接关高亮 |
| 二进制 disguised | 满屏乱码 | NUL 字节检测 |
| Tab 宽度 | 代码对齐错乱 | `tab-size: 4`，与行号栏对齐 |
| 行号与软换行冲突 | 一个逻辑行占多屏时行号只标第一行 | 关软换行时行号对齐；软换行时行号列淡化 |

## 9. 工作量估算（按本仓库的代码密度）

| 模块 | 内容 | 量级 |
| --- | --- | --- |
| Rust `text.rs` | 编码探测、解码、行索引、窗口读取、二进制检测 | 约 350 行 |
| Rust 适配 | `detect_kind` 扩展、`open_book` 分支、`pick_files` 过滤器 | 约 80 行 |
| 前端 `reader-text.js` | 渲染、虚拟滚动、行号、高亮、CSV 表格 | 约 450 行 |
| 前端适配 | kind 标签/图标/筛选/工具栏/信息面板/i18n | 约 200 行 |
| 测试 | smoke 新增断言（打开 txt / GBK / 大文件 / csv） | 约 120 行 |

总体是 3–5 个批次的量，适合按「纯文本 → 代码高亮 → CSV → 大文件」分四步交付。
